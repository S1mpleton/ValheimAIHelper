# Проверка 0.8.4

Проверка во вкладке подключения оценивает только доступность выбранной модели. В запросе нет JSON-схемы, игровых наблюдений, инвентаря, каталога, просьбы игрока и плана задач. Любой непустой текст, в том числе `{"tasks":[]}` или невалидный игровой JSON, подтверждает связь. Пул задач и его методы не вызываются; успех подключения не является оценкой качества игрового плана.

Локально прошли **643 Python-теста и 247 C#-тестов**. DLL 0.8.4 собрана без ошибок и предупреждений. Проверяются один короткий запрос, отсутствие `format` / `response_format`, лимит 16 выходных токенов, `think=false` и контекст 1024 только для проверки Ollama. Обычные игровые запросы сохраняют прежний контекст и строгую проверку JSON. Покрыты пустой ответ и ошибки API, отмена F9, повторная проверка, переключение модели и отсутствие изменений настоящего игрового пула.

Живая проверка через рабочий HTTP API службы и настоящий Ollama прошла для двух локальных моделей. **Qwen3:1.7b** ответила `OK.` за 4,293 с, включая загрузку 3,834 с; вход — 21 токен, выход — 3. **Gemma3:1b** ответила `OK.` за 2,247 с, включая загрузку 1,797 с; вход — 14 токенов, выход — 3. Каждый тест отправил один запрос без схемы и игровых данных. Режим, ревизия и существующая задача с приоритетом 67 сохранились. Эти времена относятся к машине проверки; Llama3.2:3B локально не проверялась, её весов нет в кеше.

Запуск Valheim в среде разработки недоступен. Проверки соединения не требуют запуска самой игры и не проверяют понимание игровых команд.

## Исторические результаты 0.8.3

Область проверки: отдельное значение брони NPC; отправитель речи NPC и отсутствие обратного превращения его ответов в команды человека; временное приостановление на время обмена с сохранением режима, задач и подтверждений предметных операций; возобновление при закрытии без подключения модели заново и сохранение явного F9/ручной паузы.

Для планировщика проверяются одинаковые и конфликтующие изменения одного ID до применения пула, адресная отмена сбора с сохранением других задач и один повтор исправления. Атомарная схема ограничивает цели наблюдаемыми подходящими ID; нападение на лидера из присланного сырого ответа не становится допустимым действием. Передача при несовпадении независимого разбора может пройти единственное исправление AI и повторную проверку; автоматически менять предметы, количество или приоритеты код не должен.

Локально прошли **629 Python-тестов и 247 C#-тестов**. DLL 0.8.3 собрана без ошибок и предупреждений. Прошли обмен фактическими DTO C# ↔ Python и запуск автономной службы без исходников/Python в рабочем каталоге. Проверены восемь сценариев временного обмена: сохранение задачи и аренды, F9, ручная пауза, смена провайдера, ожидающая и уже подтверждённая выдача, изменение вещей человеком во время обмена. Восемь тестов чата проверяют раздельные имена/учётную запись, локальный и отложенный callback, отсутствие переименования человека/консоли и утечки контекста между потоками.

Три дополнительных присланных экспорта оказались одинаковыми. Исходный ответ на «готовья к бою» повторно проверен по новой схеме на фактах из экспорта: врагов нет, ID цели принадлежит человеку, ветка атаки отсутствует и ответ отвергается схемой. Это проверка контракта, а не заявление об успешной подготовке моделью.

Живая проверка **Qwen3:1.7B в Ollama, think=false**, на небольших искусственных снимках не подтвердила успешное понимание трёх просьб. Для подготовки к бою модель потратила 108,8 с на повторные поиски уже известных типов предметов и исчерпала два обращения к каталогу. Проверка отмены шести сборов закончилась через 120,1 с по отдельному бюджету испытания; смысловой результат не получен, это не доказательство недопустимого плана. Для передачи одного камня модель после единственного исправления вернула пустой набор задач за 69,78 с. Предыдущие пулы сохранены, вещи не выдавались. Эти результаты отделены от регрессионных тестов, где допустимые отмена и выдача проходят весь путь проверки; исправления контракта не гарантируют понимание любой фразы небольшой моделью.

Запуск Valheim 1.0.21 в среде разработки недоступен; автоматические проверки не подтверждают отрисовку значка, реальный игровой чат или кооператив. [Сценарии проверки](actions.md#что-проверить-после-обновления).

## Исторические результаты 0.8.2


Исправление проверяет соответствие схемы ответа исполнителю: отдельные варианты `follow`, `collect`, `give`, `drop`, `action`, `goal`, обязательный приоритет от модели, типы предметов и допустимые зависимости. Проверяется одно исправление ответа с точной причиной в пределах общего тайм-аута, сохранение предыдущего пула, отмена через F9 и отсутствие автоматического назначения целей или приоритетов кодом. Отдельная матрица проверяет JSON Schema и Python-валидацию для всех трёх провайдеров. Ответы HTTP 200 без ожидаемых `choices` / `candidates` считаются ошибкой провайдера, а не успешным планом.

Локально прошли **594 Python-тестов и 239 C#-тестов**. DLL 0.8.2 собрана без ошибок и предупреждений. Прошли реальный запуск службы и обмен фактическими DTO C# ↔ Python, включая новую проверку модели на плане следования и сбора. Проверка использует вымышленный мир, сохраняет выбранные AI приоритеты и не изменяет игровой пул. Старый ответ `wait`, неверный тип предмета и неполное поручение больше не дают ложного успеха.

Дополнительные регрессии покрывают стабильную папку сохранений задач, миграцию старых папок PID, восстановление на паузе и запрет повторять неопределённые передачи. Для уведомлений обмена проверены старые и расширенные сигнатуры методов с необязательными параметрами и запасной путь через HUD. Ошибки Ollama сохраняют HTTP-код и очищенный ответ сервера; все генерации, включая исправление, используют `think=false`.

На настоящей локальной **Qwen3:1.7B, think=false**, проверка искусственного мира с 80 объектами дала 10 664 входных токена и истекла через 285 секунд на доступном CPU до получения ответа. Это ограничение времени обработки, а не доказательство неверного плана. На небольшом снимке до окончательного ограничения длительности модель выбрала правильное взаимодействие с грибом; исполнитель выдал `interact`, а искусственное подтверждение пополнения сумки завершило действие. Составная просьба выполнена не полностью: модель дополнительно поставила следование на паузу. Другой ответ правильно выбирал факел, но дважды указывал длительность 10 секунд; это воспроизведение стало причиной явного перечисления допустимых длительностей в схеме.

Живой ответ Qwen3 также выявил ошибку готовности задач: корректные `follow` с приоритетом 90 и постоянный сбор `Stone` с приоритетом 80 приводили к бесконечному следованию даже рядом с человеком. Исправление проверяет необходимость движения по границам игрового `FollowController`: остановка в 2,5 м, возобновление с 4 м, допустимый перепад высоты 1,2 м. Вблизи лидера постоянное следование сохраняется, но не занимает исполнителя, позволяя готовому сбору получить ход. Приоритеты AI при этом не изменяются.

На окончательной схеме Qwen3:1.7B вернула этот правильный план на снимке из пяти объектов за 25,4 с. Тот же исходный ответ модели без исправления целей и чисел повторно проверен новым исполнителем: лидер в 20 м → `follow:90`; лидер в 2 м → `pickup` камня по задаче `collect:80`; подтверждение камня в сумке → `interact` следующего собираемого камня; удаление лидера → `follow:90`; сближение → снова `interact`. Пройдены пять фаз, приоритеты 90/80 сохранены. Модельный ответ настоящий; координаты, изменение инвентаря и подтверждения игры в этой проверке искусственные.

Все смысловые проверки успешными не стали. На окончательной схеме Qwen3 вместо экипировки факела предложила передачу и неизвестную зависимость; повторное исправление не помогло, набор отклонён до выдачи вещей. Qwen2.5:3B на небольшом снимке с пустым пулом вернула только следование, пропустив запрошенный сбор. Самостоятельная отмена у Qwen3 сопровождалась лишним незапрошенным сбором грибов. Поэтому исправление контракта и готовности задач не означает, что любая маленькая модель корректно разберёт все составные просьбы.

Запуск Valheim 1.0.21 в среде разработки недоступен. Автоматические проверки не подтверждают физику, игровой маршрут или открытие настоящего инвентаря. [Сценарии проверки в игре](task-scheduler.md#что-проверить-в-игре).

## Исторические результаты 0.8.1

Уточнение после диагностики 0.8.2: прежняя схема действительно разрешала ответы, которые затем отвергал валидатор. Поэтому наблюдавшийся отказ сбора без типа предмета нельзя объяснять только возможностями небольшой модели. В 0.8.2 исправлен сам контракт между моделью и исполнителем.

Область проверки: обращение без имени при одинаковых именах человека/NPC, AI-план новых поручений с обязательным приоритетом каждой новой задачи, сохранение прежнего действия во время генерации, применение нового плана после подтверждения операции с инвентарём, адресные изменения задач, объединение старых дублей и очередность сбора одного приоритета. Для предметов проверяются типы `ItemDrop`/`Pickable`/`PickableItem`, дальность подхода и подтверждение взаимодействия. Для инвентаря — очередь открытия, штатный и резервный пути, перенос реальных стопок и отдельное оформление экипировки NPC.

Локально прошли 461 Python-тест и 235 C#-тестов; DLL 0.8.1 собрана без ошибок и предупреждений. Проверены реальный запуск службы и обмен фактическими DTO C# ↔ Python. Дополнительно проверены запрос неизвестного типа в каталог у всех трёх провайдеров, отсутствие лишнего поиска при обычном вопросе, запрет смешивать поиск с действиями, предел двух поисков и общий тайм-аут. Упакованная служба запускается без Python и исходников в рабочем каталоге; Windows-сборка проверяется CI перед публикацией. На настоящей Gemma3:1B воспроизведено копирование малины из старого контекста. После удаления примеров окончательный полный AI-план на запрос топора всё ещё оказался недопустимым: модель выбрала сбор без типа предмета. План был отклонён, прежний пул сохранён. Мы не подменяем решение слабой модели нативными целями или приоритетами. Это ограничение модели на проверенном запросе; успешное поведение в игре не заявляется.

Текущие изменения не считаются подтверждением фактического открытия окна или визуального оформления в Valheim 1.0.21: игра в среде разработки недоступна. [Сценарии проверки в игре](task-scheduler.md#что-проверить-в-игре).

- 41 C#-тест: политика действий, сериализация, ограниченный ввод, безопасный loopback-адрес и чтение статуса игровым интерфейсом.
- Сборка плагина net48 против Valheim 0.221.4: без ошибок и предупреждений.
- Межъязыковая проверка фактического C# JSON → Python HTTP API → C#: решения, а также DTO новой игровой панели для настроек, списка OpenAI, проверки модели и стопа. Проверяются обе формы успешного ответа API: настройки с key_present и команды с revision.
- Отдельный HTTP-процесс: сопряжение, наблюдения, диагностика 422, следование и стоп. Синтаксис дополнительной веб-панели проверен Node.

Живые проверки официальных API с разрешения пользователя:

- OpenAI gpt-6-luna: HTTP 200, простой ответ OK за 1,6 секунды. Через настоящий адаптер и схему действий: валидный wait и «Связь работает» за 4,2 секунды.
- Gemini gemini-3.8-flash: список и карточка модели HTTP 200. Обычный короткий запрос не ответил за 30 секунд. MINIMAL был отклонён HTTP 400; LOW принят, но генерация вернула HTTP 503 с сообщением о высокой нагрузке.
- Реальные игровые данные не отправлялись. Ключи использовались только в памяти процессов и не включены в код/пакет. Остальные тесты используют подставные HTTP-ответы.

Не проверены: настоящий процесс Valheim, отрисовка кнопки и панели, мышь/клавиатура внутри Unity, навигация игрового меню контроллером, сетевое движение и совместимость с Valheim 1.0.21. Для этих проверок требуется установленная игра; сборка и межъязыковые тесты не заменяют игровой запуск. PowerShell-установщик не запускался против установленной игры. В Windows CI добавлена проверка синтаксиса пусковых скриптов.
