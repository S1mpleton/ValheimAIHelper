# Каталог и выбор предметов — 0.8.1

Мод строит каталог из `ObjectDB` запущенной игры: корректные prefab с `ItemDrop`, включая предметы других модов. Каталог описывает типы вещей, а наблюдение — доступные NPC предметы. Построение каталога не создаёт предметы и не разыгрывает случайный лут.

## Полный список

После загрузки базы игры каталог сохраняется в:

```text
BepInEx/config/ValheimAIHelper/item-catalog.json
```

Файл содержит версию игры, язык, версию каталога, число типов `total` и массив `items`. Запись заменяется целиком после подготовки нового файла.

| Поле | Значение |
|---|---|
| `item_prefab` | Стабильный тип из игры: `Stone`, `Raspberry`, `AxeStone` и другие |
| `name` | Название на текущем языке игры |
| `token` | Токен локализации, например `$item_stone` |
| `category` | Категория игровых данных ItemDrop |

Наличие `AxeStone` в словаре не означает, что топор лежит рядом. Закрытые сундуки и незагруженные области не раскрываются.

## Выпавшие вещи и предметы через E

В 0.8.1 наблюдение различает:

- **`ItemDrop`** — выпавшая стопка, подбираемая действием `pickup`.
- **`Pickable` / `PickableItem`** — растение либо лежащий в мире предмет, который ещё нужно собрать через E. Для него используются `interact` и объявленный результат `produces`.
- **Ресурс** — дерево или залежь, для которых могут понадобиться топор/кирка и действие `gather`.

Камень, одуванчик или топор, доступный через E, не становится добываемой залежью и не требует кирки. Тип результата берётся из объявленного prefab или уже выбранного визуального предмета. Случайная таблица не разыгрывается ради наблюдения. Суффикс экземпляра `(Clone)` не меняет стабильный тип вещи.

Сканируются загруженные доступные объекты до 128 м. Общий список выпавших и собираемых через E целей ограничен 80 записями; разные типы получают представительство, чтобы множество ягод не вытесняло топор. Реестр ItemDrop дополняется кешируемой проверкой загруженных сцен. Экипировка персонажей, предметы на стойках и визуальные дочерние объекты растения не выдаются за отдельные выпавшие стопки.

Для сбора через E исполнитель подходит к цели, отправляет взаимодействие один раз и ожидает подтверждение: растение собрано, появился соответствующий выпавший предмет либо изменился инвентарь. Сетевая задержка не вызывает повторный RPC на каждом тике; ожидание ограничено игровым временем. Подбор результата затем подтверждается сумкой NPC.

## Что получает модель

У предметов в сумке и мире есть стабильные `item_prefab`/`item_token`; у собираемых целей — `produces`. Передача каталога ограничена 4096 определениями со счётчиками полного количества и усечения; экспорт JSON содержит весь список. После подтверждения версии каталога мод не повторяет его целиком в каждом снимке.

Для `/api/decision` и `/api/tasks/context` действует лимит 2 МиБ; остальные маршруты ограничены 128 КиБ. Начальный запрос планировщика получает только типы реально наблюдаемых вещей. Для неизвестного или неоднозначного названия модель может вернуть `catalog_queries`: служба выдаёт ограниченные совпадения из полного игрового каталога и повторно просит план. До двух таких обращений укладываются в общий тайм-аут; запрос словаря не исполняет действий. Поиск виден в журнале диалога как `catalog-lookup`. Обычная просьба или разговор не требуют отправки полного каталога. Словарное совпадение описывает тип, а не наличие предмета в мире.

AI получает полный формат плана: сам выбирает задачи, приоритет каждой новой задачи и зависимости. Готовые задания с малиной и специальные нативные шаблоны для маленькой модели не подставляются. Нативный планировщик проверяет результат и связывает выбранные типы с подходящими целями свежего наблюдения. Ошибка модели не превращается в подстановку другой задачи или предмета.

Передача/сброс дополнительно разбираются по исходному поручению (`task-transfer`): код сравнивает тип операции, предметы, количество и область выдачи с предложенным планом. Для всей сумки есть проверка `task-scope`. При несовпадении новый набор отклоняется, а прежняя работа сохраняется. Модель может ошибиться и на проверке, поэтому корректный JSON не гарантирует правильного понимания.

## Как проверить

| Поручение | Нужная цель |
|---|---|
| «Возьми каменный топор» | Реальный `AxeStone` в выпавших вещах либо среди собираемых через E |
| «Собирай одуванчики» | `Dandelion` на земле либо цель с соответствующим `produces` |
| «Собирай малину» | Куст с `produces=Raspberry` или выпавшие ягоды |
| «Дай три камня» | Точное количество 3 из сумки NPC |
| «Не нужно больше собирать малину» | Отмена соответствующей задачи; другие задачи сохраняются |

Откройте «Журнал → Копировать отчёт». **`dropped items`** перечисляет выпавшие вещи, **`E collectibles`** — цели взаимодействия с типами результата. Если топор виден игроку, но отсутствует в обоих списках, приложите этот отчёт; если он наблюдается, сохраните также «Диалог AI», чтобы различить ошибку наблюдения и разбора поручения.

Все запросы Ollama используют `think=false`. Разбор адресата помечен `chat-intent`, нового пула — `tasks`, сложной цели — `task-step`. [Инвентарь NPC](npc.md#открыть-инвентарь-npc) · [Планировщик и проверки](task-scheduler.md#что-проверить-в-игре).
